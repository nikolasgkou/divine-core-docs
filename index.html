The premise

a report written by the agent is not evidence about the agent

An agent that writes code also writes the summary of that code. It can run a suite, skip it, read a stale build, quietly relax a test, or simply state that everything is green — and all of those produce the same artefact: a confident paragraph.

Divine Core treats that paragraph as untrusted input. Permission is a recorded fact attached to a launch. For builder tasks, completion depends on checks the daemon runs against a disposable copy and binds to one exact source fingerprint. The interesting engineering is in the space between the agent and the merge button.

It built itself

the harness is its own first subject

Divine Core is written by agents running under Divine Core. The system that decides whether an agent's work is finished has been deciding that about its own source since its third day of existence. Every number below comes from the daemon's live PostgreSQL — not from a changelog.

Of those launches, 16 were builders, 7 reviewers, 4 spec workers. The seven reviews produced 56 checklist answers — seven reviews times eight topics, none skipped, because the schema does not allow a topic to be left out — along with 17 findings and 13 topics marked as a concern.

The repository went from empty to a self-hosting harness in about a week. That is not a claim about velocity; it is the reason the guardrails had to exist first. A system producing changes this fast is exactly the system you cannot afford to trust on its own account.

System architecture

one application · one source of truth · local-first

One Spring Boot application, one Maven module, one daemon. PostgreSQL owns task identity, launch rows, workspaces, frozen check contracts and measured evidence — not a set of competing registries and status files. Spring Events wake consumers in-process, but critical pending work is persisted in the same transaction as the state change that triggered it, because neither events nor a database alone make an external effect exactly-once.

MCP is the primary agent-facing interface, over Streamable HTTP, so more than one client can drive the same long-lived daemon. An MCP connection is not a task identity: a client can disconnect and reconnect without losing tasks or repeating a completed side effect.

Three roles and the surface they reach

spec → decide → build → verify → review → integrate

read-only

spec

Turns a request into acceptance criteria, sourced findings and explicit open questions — each with the worker's own recommendation and who must decide it.

The orchestrator answers every open question before a builder starts. A builder left to guess guesses what is easiest to test.

scoped write

builder

Implementation, refactoring and migrations inside its own git worktree and its own declared edit scope.

It asks the daemon to verify; it cannot verify itself, cannot change what will be checked, and cannot report success past a failed check.

read-only

reviewer

Answers a fixed checklist of the failures a green suite does not catch, with a verdict per topic and concrete findings behind every concern.

The checklist is part of the tool schema, so a topic cannot be silently left out.

Task lifecycle

four states · one gate · failure never blocked

finish_task refuses COMPLETED from a spec worker with no spec, a reviewer with no review, and a builder whose verification does not match its final snapshot. The opposite direction is deliberately open: a blocked worker can always report FAILED, immediately and without evidence, because a worker that cannot say "I am stuck" will invent something that looks like progress.

Verification the worker cannot author

freeze before launch · run in a snapshot · bind the verdict to the source

  • Frozen before the process exists. Named checks — argv, timeout, which report globs must exist and must contain executed tests — are written once, before launch, and are immutable. A concurrent configure and default-freeze race is settled by an insert-if-absent, not by a merge that could replace the winner's contract.
  • Run in a throwaway copy. The daemon fingerprints the candidate worktree, snapshots it, deletes any pre-existing reports inside the copy, and runs the frozen argv there. Deletion never touches a real checkout.
  • Only reports that run produced. JUnit XML is parsed with DTD and external-entity resolution disabled, leaf suites only so parent totals cannot double-count, with a per-report size ceiling. A required scope that exists but executed nothing counts as missing; a skipped-only suite fails.
  • Re-fingerprinted afterwards. If anything moved while the checks ran, a synthetic snapshot-integrity failure is appended and the result cannot pass.
  • Serialised, not interleaved. A workspace lock and a per-repository run gate refuse a second concurrent verification cheaply rather than letting two runs share a tree.
  • Output is not a place for secrets. Build stdout is discarded rather than persisted; what is stored is counts, report paths, exit code, duration and a diagnostic line.

Permission as a durable fact

a validated, versioned artefact — not a sentence in a prompt

The catalog fails closed

Roles live in a versioned registry: owner, scope, pinned policy schema, version, and the test that exercises it. The daemon loads and validates all of it at startup and refuses to boot on a malformed file, a duplicate, a registry/file disagreement, an unknown MCP profile, a rule that is both allowed and denied, or anything orphaned in either direction.

There is no implicit role and no default policy. An ambiguous conflict is rejected at load rather than resolved silently later.

Read-only role policy

A role declared read-only is validated as such at load: it may not list an editing tool, and if it inherits a default tool set it must deny the editing tools by name.

Each worker also receives its own filtered MCP config containing only its profile's servers. Secrets are passed as a path the launcher reads at exec time, so no token value reaches an argv, a process environment, or a log line.

The review checklist

eight questions a passing suite does not answer

A reviewer asked to "look for problems" reports the problems it happened to notice, and the ones it never thought to look for are indistinguishable from the ones that are not there. So the list is part of the schema, and every topic must be answered.

BOUNDSEvery loop, queue, retry and read has an upper bound, or a reason it cannot grow.
TIMEOUTSAnything that can block has a timeout. "It has never hung" is not a bound.
RECURRINGTicks, retries and reconcilers are idempotent and accumulate nothing.
CONCURRENCYTwo identical calls at once: races, shared mutable state, and whether the second is cleanly refused.
QUOTAA worker that can loop is a worker that can spend. Is there a cap, and is refusal cheap?
PARTIAL_FAILUREWhat an exception halfway through leaves behind: half-written rows, held locks, temp directories.
UNTRUSTED_INPUTWhere outside values end up — command line, query, path, log — including values the daemon itself stored earlier.
TEST_INTEGRITYAssertions that cannot fail, code special-cased to test inputs, behaviour bent to suit a test.

Here is one it actually caught, filed under CONCURRENCY against a change whose tests were entirely green:

summary   Cross-job cache-key reuse lookup in runJob is unguarded
          for backends without an installation lock
file      src/main/java/local/divine/core/moderne/ModerneService.java:244
severity  minor
status    open · filed, not yet fixed
detail    Read + reasoned, not executed. Before this delta the cached-success
          lookup ran only while holding the installation FileLock. After the
          refactor runJob() is invoked directly, with no lock, whenever
          installationLockPath() is null — true for OpenRewriteMavenBackend.
          Two threads with an identical cache_key can both miss the cached row
          and both execute. No state is corrupted; the intended cross-task
          cache reuse is silently dropped. Not a correctness bug, so minor.

No test suite would have reported that, because nothing was broken — only quietly wasteful, and only under a race. It is still open, and it is on this page for the same reason it is in the database: a gap you have named costs less than one you have not. Note also what the reviewer says about itself — read and reasoned, not executed. A finding that states its own method is a finding you can weigh.

Recipes with a chain of custody

OpenRewrite · typed analysis · preview before mutation · verify after application

Divine gives agents access to OpenRewrite's open-source recipe ecosystem without turning a recipe into unchecked write authority. An agent can search the catalog, inspect the exact recipe and version, run analysis against its task snapshot, and request a preview. Search recipes answer questions such as “where is this method called?” or “why is this dependency present?” with source-attributed results. Transformation recipes produce a patch for inspection.

01 · DISCOVERSearch recipesFindMethods, FindTypes, dependency insight, migrations and cleanup.
02 · PINDescribe exactlyResolve the recipe, version, typed options and runtime revision.
03 · SNAPSHOTAnalyse a copyRun offline against the fingerprinted task source, with no network.
04 · PREVIEWInspect the patchKeep diagnostics and data tables separate from source mutation.
05 · PROVEApply, then verifyEnforce task path scope and rerun the frozen candidate checks.

Semantic tooling becomes evidence, not authority. A successful recipe run does not declare the work complete. Preview application is rejected if its source snapshot is stale or if the patch escapes the task's allowed paths; the resulting candidate must still pass the same source-bound verification gate.

The backend is disabled by default and inert until an operator provisions it: a pinned runtime revision, a checksum-verified executable, a local Maven repository, and execution in a network-isolated namespace with the build in offline mode. Reaching the open-source recipe ecosystem should not quietly become an outbound dependency at build time.

code intelligence

Questions across a codebase

Recipes can trace method calls, type usage, annotations, imports, deprecated APIs and Maven dependency paths. Results remain attached to the source snapshot that produced them.

controlled transformation

Mechanical change, human-readable patch

API renames, import cleanup, static analysis fixes and Java migrations are previewed first. The patch enters the same scoped workspace and verification flow as agent-written code.

Operating it

three things that broke, and the failures it is built to survive

01 · silence is expensive

A client timeout burned real quota

The MCP client gives up on a tool call after 60 seconds. The proof run took longer. The daemon finished it and recorded the result; the worker saw only “the operation timed out”, retried, and spent its run budget redoing work that was already done.

Fix: the client timeout is raised above the daemon's own, so the daemon's verdict — including TIMED_OUT — is what reaches the worker, rather than silence.

02 · an empty list is a claim

tools: [] means none, not default

An empty allowlist is passed through verbatim: "only these, which is none". Reading it as "no preference, use the defaults" would silently hand a worker the full built-in tool set.

The distinction is now explicit in the launcher and asserted in tests, because a permissions bug that widens access looks exactly like a permissions bug that does nothing.

03 · the race before the race

Why the contract is an insert, not a merge

Freezing verification requirements used to go through an ordinary save. Two paths can reach it at once — an explicit configure and the default freeze at launch.

A merge would let the loser replace the winner's frozen requirements before anything had been measured against them. It is an insert-if-absent now: the first contract wins, and the second is refused.

Failure modes it is designed for

  • Daemon restart: pending work is rediscovered from the database, not from memory.
  • A launch that never confirmed a session is adopted or relaunched, not orphaned.
  • Concurrent verification on one repository is refused with BUSY rather than interleaved.
  • Finished tmux sessions are archived on a delay, leaving the transcript readable.
  • A worker's task id is its session id, so its native transcript is findable from the task row alone.

Known gaps, stated as gaps

  • A CLAIMED task whose worker stopped responding has no automatic recovery: it is stopped and restarted by hand.
  • A tool policy is a recorded permission boundary and an audit trail; it is not an OS sandbox for write-capable workers.
  • Verification proves a suite ran and passed against a known tree — not that its assertions are worth making. That is why TEST_INTEGRITY is a reviewed topic, not a metric.

How it is built

Package boundaries are enforced by ArchUnit rather than by convention. Persistence, migrations and MCP wiring are exercised against real PostgreSQL through Testcontainers. The tmux launcher, inspector and archiver are tested against a real scratch tmux server rather than a mock, because the failures worth catching there are the ones a mock agrees to pretend away.

Design constraints, chosen deliberately

  • Single workstation, no external broker, no Redis, no Kubernetes.
  • Local-first control state: workspaces, policy records, evidence and local-model artifacts remain on the workstation. Codex and Claude use their configured inference providers.
  • One module until a boundary earns its own package — no layers added to satisfy a pattern.

Lineage and direction

  • Before: a Python control plane with runner hooks, task admission, resource leases, durable handovers and Bubblewrap-isolated read-only execution. It proved the model and outgrew flat files as the source of truth.
  • Now: one Spring Boot service over PostgreSQL, driven through MCP by any compliant client.
  • Next: a profile-driven local model runtime, whose preflight refuses rather than silently substituting a different model, wired in so bounded repetitive loops run locally under the same verification requirements.

Why this exists

the part that is not a mechanism

Most of the argument about coding agents is about how much they can write. That was never the constraint I ran into. The constraint is that an agent's output arrives with a confidence level it has not earned, at a rate no reviewer can absorb, and the reviewer who gives up first is the human.

So the thing worth building was not a better agent. It was the apparatus around one: somewhere the permissions are written down before the work starts, somewhere the work happens that is not your checkout, and something that measures the result and is willing to say no. Speed is only an asset if refusal is cheap.

The rest of it — the digests, the frozen contracts, the eight questions — is just what that principle looks like once it has to survive contact with two agents running at once.
