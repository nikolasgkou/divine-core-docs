01 · The review loop

Follow the dependency.
Question the old evidence.

Suppose a promotion function changes from requiring both review and checks to accepting either. Its linked claim still says both are required. The change creates a review obligation; only meaningful checks can establish what the new code does.

  1. Capture the context for the right candidate. The task, checkout, source snapshot and plan digest identify which intent and declarations the agent is reading.
  2. Review the affected relationships. Compare source and plan definitions, follow related concepts and covering steps, and expose missing links or unknown baselines.
  3. Measure the changed behavior. Fresh verifier executions support only the declared checks on their recorded inputs. A rationale annotation is not an execution.
  4. Regenerate after authored changes. Humans and agents receive projections of the same inputs, with hashes that detect changed inputs or manually edited output.

Javadoc and annotations link symbols to stable concept IDs. The plan DSL holds definitions, decisions, original intent, dependencies and acceptance obligations. Those links require deliberate maintenance.

Immutable Git document content and provenance enter the existing knowledge store. A bounded corpus query can surface that material as UNREVIEWED and UNVERIFIED. Retrieval alone does not turn narrative into a reviewed claim.
